The snake that turned a frame too late

A terminal game with no engine, no libraries and one bug that only appeared when you got good at it.

Written by Aditya Chandra Prajapati Nov 2025 ~1,400 lines of C++

I wanted to build a game without an engine. Not because engines are bad, but because I had never once written the loop myself — the part that decides what a frame is, and what happens inside it. Everything I had made until then sat on top of something that already answered that question.

The problem

A snake game is the smallest program that still needs all of it: input that cannot block, a world that updates on a clock, and a renderer that draws whatever the world currently is. Get any of the three wrong and it is immediately obvious, which is exactly why it is worth building.

The approach

Plain C++ and the terminal. The snake body is a queue — push a new head, pop the tail, and the whole movement problem disappears into a data structure. No array shuffling, no per-segment update.

It played perfectly until I got good at it. Then, at speed, the snake would occasionally eat itself through a corner it had clearly already left. The bug that was worth the project

What broke

Collision detection ran after the render. At low speed nobody notices — the wrong frame is on screen for 80 milliseconds. At high speed the snake is drawn in a position it has already moved out of, and the check runs against the drawn position rather than the real one. Moving the check above the render fixed it in one line.

Where it stands

It plays clean at every speed I can handle. Because it is plain C++ with no dependencies, it compiles to WebAssembly — which means the version you would play is the same code, not a rewrite.
